## はじめに

仕事では Jira でチケットを切り、GitHub の PR にリンクしてスプリントを回しています。iOS アプリの個人開発を始めるにあたって、**そのプロセスをどこまで持ち込むか** を最初に決めました。

結論から書くと、こうなりました。

| 仕事で使っているもの | 個人開発 |
|---|---|
| Jira（チケット・スプリント） | ❌ 捨てた |
| GitHub Projects（カンバン） | ❌ 使わない |
| CI（ビルド・テスト自動化） | ⏸ 保留 |
| Issue と Milestone | ✅ 残した |
| ブランチと PR | ✅ 残した |
| コードレビュー | ✅ 形を変えて残した |

判断の基準はひとつです。**「その仕組みが解いていた問題は、ここにも存在するか」**

---

## 捨てたもの

### Jira とスプリント

Jira が解いているのは **複数人の作業を調整し、進捗を関係者へ報告する** 問題です。

ひとりの個人開発には、調整する相手も報告する相手もいません。ベロシティを測っても、その数字を見るのは自分だけです。スプリントの区切りに意味を持たせる外部要因もありません。

加えて、**同じ役割を果たすものが既にありました。** 開発を始める前に v1.0 のステップを10個に分けて書き出していたので、それがそのままバックログになります。ここへさらに Jira を重ねると、チケットを起票して状態を動かす作業だけが純粋なオーバーヘッドとして残ります。

### GitHub Projects（カンバン）

Milestone の上位概念だと思っていたのですが、違いました。**別の軸です。**

| | Milestone | Projects |
|---|---|---|
| 役割 | 「このバージョンに何が入るか」（分類） | 「今どれがどの段階か」（進行状態） |
| 範囲 | リポジトリ1つ | **複数リポジトリを横断できる** |
| 表現 | 進捗バー1本 | カンバン、テーブル、ロードマップ |

Projects が効いてくるのは、複数リポジトリ・複数担当者の作業をひとつの画面で調整する場面です。これは Jira が解いていたのと同じ問題で、同じ理由で今は要りません。

Issue が10個、担当者が1人なら、リポジトリの Issues タブだけで足ります。

### CI

これは「不要」ではなく **「まだ早い」** です。2つ理由があります。

**テストがまだありません。** Xcode が生成したテストターゲットは空のテンプレートだけで、CI が自動で止めてくれる「デグレ」がまだ存在しません。今 CI を作っても、できるのはビルドが通るかの確認だけです。それはローカルで毎回やっています。

**そして macOS ランナーは高くつきます。** GitHub Actions のランナーは OS ごとに消費レートが違い、**macOS は分あたり10倍** で計算されます。プライベートリポジトリの無料枠が月2,000分でも、macOS 換算では実質200分程度です。Xcode のビルドは1回数分かかるので、push のたびに回せば月内に使い切ります。

導入するとすれば、純粋なロジックにユニットテストが増えてきた頃か、TestFlight 配布の直前です。

:::message
逆に、Xcode を必要としない処理（後述のレビュー自動化など）は Linux ランナーで回せるので、この10倍の制約を受けません。「CI は高い」と一括りにせず、**何を回すかで分けて考える** 必要がありました。
:::

## 残したもの

### Issue = ステップ、Milestone = バージョン

対応を固定しました。

```
Milestone v1.0 ─┬─ #1  Xcode プロジェクト + 実機実行      ✅
                ├─ #2  SwiftUI の基礎（View, State）      ✅
                ├─ #3  カメラ権限 + プレビュー            ✅
                ├─ #4  シャッターで撮影
                │   …
                └─ #10 アプリアイコン + TestFlight

Milestone v1.1 ── #11 グループ共有の基盤
Milestone v1.2 ── #12 オブジェクト除去
Milestone v1.3 ── #13 顔補正
```

ポイントは、**着手前にロードマップ全体を Issue として並べておく** ことです。こうすると Milestone の進捗バーがそのまま「v1.0 の何割が終わったか」になります。1本ずつ起票していく方式だと、全体像がどこにも存在しません。

ラベルは `feature` / `fix` / `chore` の3つだけにしました。ブランチの接頭辞と対応させています。増やしても分類に迷うだけで、検索する相手がいないので意味がありません。

### ブランチと PR

**ひとりなのに PR を作るのか**、というのが一番迷った点でした。レビューする相手がいないなら、`main` へ直接コミットしても同じではないか、と。

実際にやってみて、相手がいなくても効く理由が3つありました。

**差分をまとめて見返す機会になります。** コミット単位で書いている間は部分しか見ていません。PR の画面で1つの塊として眺めると、消し忘れたコードや揃っていない命名がそこで見つかります。

**`main` が常に動く状態で保たれます。** 作業途中のコードが `main` に混ざらないので、「今の `main` を実機に入れれば動く」が保証されます。

**あとから読む自分のための記録になります。** ステップ10まで進んだ頃に「ステップ2で何を悩んだか」は覚えていません。PR 本文がその記録になります。

ブランチ名は Jira 時代の `feature/XX-123` をそのまま持ち込みました。チケット番号を Issue 番号に置き換えるだけです。

```
feature/{Issue番号}-{英語の要約}
例: feature/3-camera-permission-preview
```

Issue 番号はリポジトリ内で一意なので、Jira のようなプロジェクトキーが要らないぶん短くなります。

PR 本文はテンプレートを置いて、4つの見出しだけにしました。

```markdown
## Overview
## UI Changes
## Details
## Test

Closes #
```

空の見出しは消してよい運用にしています。埋めること自体が目的になると、形式的な文章が増えるだけなので。

`Closes #N` を書いておくと、マージ時に Issue が自動で閉じます。**ブランチ名に Issue 番号を入れても自動では閉じません**（あれは人が読むための慣習です）。閉じるのはこのキーワードの役割です。

### レビュー — 相手がいない問題をどう埋めたか

仕事では Copilot のレビューが走ります。個人プロジェクトでは、**Claude Code の `/code-review`** を使うことにしました。GitHub 側の課金が発生せず、既に払っているサブスクリプションの範囲で処理されます。

実際に出てきた指摘の例です。

- `defer` の位置は正しいが、`permissionDenied` フラグが権限以外の失敗も兼ねていて、権限を許可した後も「権限を許可してください」と表示され続ける経路がある
- `ignoresSafeArea()` が背景ではなく中身側に付いていて、意図と対象が逆になっている
- `stop()` を定義したが呼び出し箇所がない

見つけた指摘はインラインコメントとして PR に残し、直したら該当コミットへのリンクを返信してスレッドを閉じています。**「何を指摘され、どのコミットで直したか」が PR に残る** ので、レビューの有無にかかわらず記録としては機能します。

すぐ直さないものは、対応予定のステップの Issue 本文へ書き足しておきます。PR のコメントに残したままだとマージと同時に埋もれるので。

## 設定として固定したこと

毎回迷わないように、リポジトリ側で決めておいたものです。

**Squash マージのみ許可。** マージコミットとリベースは設定で無効にしました。ステップ単位の PR がそれぞれ1コミットになるので、`main` の履歴がそのままステップの一覧になります。

```bash
gh api repos/<owner>/<repo> -X PATCH \
  -F allow_squash_merge=true \
  -F allow_merge_commit=false \
  -F allow_rebase_merge=false \
  -F delete_branch_on_merge=true \
  -f squash_merge_commit_title=PR_TITLE \
  -f squash_merge_commit_message=PR_BODY
```

**マージ後のブランチ自動削除も有効にしました。** ただしローカルは残るので、自分で消す必要があります。ここで一度引っかかりました。

```
$ git branch -d feature/2-swiftui-basics
error: the branch 'feature/2-swiftui-basics' is not fully merged
```

Squash は新しいコミットを1つ作る方式なので、**Git から見ると元のコミットは `main` の祖先になっていません**。マージ済みと判定できないため、安全側に倒して拒否されます。リモートで消えたことを確認したうえで `-D` を使えば問題ありません。

## まとめ

振り返ると、判断はすべて同じ形をしていました。

> **その仕組みが解いていた問題は、ここにも存在するか。**

Jira とカンバンが解いていたのは「複数人の調整」でした。ひとりならその問題自体がないので、一緒に捨てられます。

一方で PR が解いているのは「変更をひとつの塊として見返す」ことです。これはレビュアーがいなくても残る問題なので、形を変えて残しました。

CI が解くのは「壊れたことに早く気づく」ことです。壊れたと判定する材料（テスト）がまだないので、今は保留にしています。

仕事のプロセスをそのまま持ち込むと重すぎ、全部捨てると記録が何も残りません。**道具ではなく、道具が解いていた問題のほうを見る** と、どちらでもない線が引けました。
