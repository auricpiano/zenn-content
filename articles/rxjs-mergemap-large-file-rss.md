## はじめに

大小さまざまなファイルをアップロードして別のストレージへ連携する、という処理を担当しています。負荷テストを実施したところアプリケーションが停止し、原因を追ってみると **性質の異なる2つの問題が重なっていた** ことが分かりました。

1. 並列処理の書き方（RxJS のオペレータ選択）による待ち行列の詰まり
2. 処理後にメモリが OS へ返らない問題

どちらも「知っていれば一瞬、知らないと延々ハマる」種類のもので、自分は後者でした。同じ構成でつまずく人がいそうなので、**何をどう切り分けて、なぜその対応を選んだのか**を残しておきます。

コードは実際のものではなく、構造だけを再現した最小の例です。

## 前提 — 処理の形

- ファイルの発生をイベントとして受け取り、順次アップロードする
- **ファイルサイズの分散が極端に大きい**。小さいものは数MB、大きいものは数GB
- 1回の処理で数千件が一気に流れてくることがある

この「サイズの分散が大きい」という点が、後述の問題1の引き金になります。

## 起きたこと

負荷テストでアプリケーションが停止しました。停止の直前、次の2つが観測できました。

- 小さいファイルの連携が、明らかに不自然なタイミングで止まっている
- メモリ使用量が処理の進行とともに右肩上がりで、下がらない

この2つを **同じ原因だと思って追いかけたのが最初の失敗** でした。実際は独立した別の問題で、切り分けてからは早かったです。

## 問題1: `concatMap` による head-of-line blocking

### 元の実装

概念的には、こういう形でした。

```ts
fileEvents$
  .pipe(
    bufferTime(1_000),
    concatMap((files) => processBatch(files)),
  )
  .subscribe();
```

一定時間バッファに溜めて、バッファ単位で順番に処理する。一見まっとうに見えます。

### `concatMap` が保証していること

`concatMap` は **前の inner Observable が complete するまで次を始めません**。つまり同時実行数が常に 1 で、順序が保証されます。

順序が意味を持つ処理ならこれが正解です。しかし今回は「どのファイルが先に連携されるか」に要件上の意味がありませんでした。**必要のない保証のために直列化していた** わけです。

### なぜサイズの分散が効くのか

バッファに数GBのファイルが1つ混ざると、そのバッファの処理が終わるまで **次のバッファ全体が待たされます**。

```
バッファ1: [小, 小, 巨大, 小]  ← 巨大が終わるまで完了しない
バッファ2: [小, 小, 小, 小]    ← ずっと待機
バッファ3: ...                  ← ずっと待機
```

先頭の要素が後続すべてを塞ぐ、いわゆる **head-of-line blocking** です。数百件の小さいファイルが、1つの大きなファイルの後ろで待ち続けていました。

### `mergeMap` に変える、その代償も引き受ける

`mergeMap` は inner Observable を並行して購読します。終わったものから順に流れるので、詰まりは解消します。

ただし **`mergeMap` の同時実行数は既定で無制限** です。数千件のイベントが来たら数千件を同時に開こうとします。詰まりを直してメモリを壊す、では意味がありません。

そこで第2引数で明示的に上限を置きました。

```ts
const CONCURRENCY = 6;

fileEvents$
  .pipe(
    mergeMap((file) => processFile(file), CONCURRENCY),
  )
  .subscribe();
```

あわせて `bufferTime` も外しました。ファイル単位で流すなら、まとめる意味がありません。

`6` という数字は、後述の計測でメモリのピークが許容範囲に収まる値として決めました。理論から導いた数ではなく、**測って決めた数** です。

:::message
`concatMap` / `mergeMap` / `switchMap` / `exhaustMap` はいずれも「内側の Observable をどう平坦化するか」の戦略の違いです。順序保証が必要なら `concatMap`、最新だけ欲しいなら `switchMap`、処理中の新規を捨てるなら `exhaustMap`。**今回の学びは「速いオペレータに変えた」ではなく「不要な保証を外した」** という整理でした。
:::

## 問題2: heap は減っているのに RSS が下がらない

詰まりが解消しても、メモリが下がらない問題は残りました。

### heap しか見ていなかった

最初は V8 のヒープを見ていて、「使用量は増えていないのにおかしい」と思っていました。ここが理解不足でした。

`process.memoryUsage()` が返す値は、見ている対象が違います。

```ts
const { heapUsed, heapTotal, external, rss } = process.memoryUsage();
```

| 項目 | 何を指すか |
| --- | --- |
| `heapUsed` / `heapTotal` | V8 ヒープ。**JS オブジェクトが住んでいる領域** |
| `external` | V8 が管理する JS 外のメモリ（`Buffer` など） |
| `rss` | Resident Set Size。**プロセスが実際に占有している物理メモリの総量** |

大きなファイルを扱うと、実体は `Buffer` としてヒープの外に確保されます。**ヒープだけ見ていると、増えているものが見えません。** コンテナの上限に当たって落ちるのは RSS のほうです。

RSS を見たら、期待どおりには下がっていませんでした。

### glibc malloc は OS にすぐ返さない

`free()` されたメモリが即座に OS へ返るわけではない、というのがここでの本題でした。

glibc の malloc は解放された領域を arena に保持して再利用に備えます。通常は妥当な戦略ですが、**サイズがばらばらな確保と解放を大量に繰り返す** と断片化が進み、arena が空かないまま RSS が高止まりします。今回の「数MBと数GBが混在する」という性質が、これを踏みやすい形でした。

### jemalloc に差し替える

jemalloc は断片化に強く、OS への返却もより積極的です。アロケータの差し替えは `LD_PRELOAD` で、アプリケーションのコードを変えずに行えます。

```dockerfile
# Debian 系のイメージの場合
RUN apt-get update \
 && apt-get install -y --no-install-recommends libjemalloc2 \
 && rm -rf /var/lib/apt/lists/*

ENV LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2
```

```dockerfile
# Alpine の場合
RUN apk add --no-cache jemalloc
ENV LD_PRELOAD=/usr/lib/libjemalloc.so.2
```

ライブラリのパスはディストリビューションとアーキテクチャで変わるので、`find / -name 'libjemalloc*'` で確認してから指定するのが安全です。

これで、処理が終わったあとに RSS が実際に下がるようになりました。

:::message alert
アロケータの差し替えは挙動そのものを変える対応です。**入れる前後で必ず計測して、効いていることを確認してください。** 「入れたから大丈夫」で済ませられる類の変更ではありません。
:::

## 計測 — 何をどう見たか

対応の前後で、次を並べて見ました。

- **RSS の推移**（メインの指標）
- heap の推移（RSS との差分から、ヒープ外の増加を読むため）
- 処理の完了までの時間

グラフに並べると、RSS が上がって下がる山が処理単位で見えるようになり、**「返っていない」のか「そもそも確保が多い」のか** を区別できました。この区別ができるまでは、対応が効いているのかどうかも判断できていませんでした。

そして最終的に、扱う想定の最大構成でメモリのピークがコンテナ割当の半分以下に収まることを確認して、上限値を決めました。

## まとめ — 判断として残ったこと

技術的な結論より、判断の順序のほうが再利用できると思っています。

1. **症状を1つの原因に決めつけない。** 詰まりとメモリは別問題でした。切り分けてから解決が早くなりました
2. **要件が求めていない保証を外す。** `concatMap` は正しく動いていました。要件に対して過剰だっただけです
3. **速くする変更は、必ず別のリソースを圧迫する。** `mergeMap` に変えるなら同時実行数の上限を同時に決める。片方だけやると別の場所が壊れます
4. **見ている指標が対象を捉えているか確認する。** heap を見ながら「増えていない」と言っていた時間が一番長かったです
5. **数字は測って決める。** 同時実行数 6 も、コンテナ割当も、理論から出した値ではありません

## 補足: AI との進め方について

この対応では、解決策の候補そのものは AI と検索から得ました。`mergeMap` への変更も jemalloc も、自分の引き出しには無かったものです。RSS と heap の区別すら、この時に調べて理解しました。

そのうえで実際にやったのは、こういう順序でした。

- 症状を **「順序待ちの問題」と「メモリが返らない問題」に切り分ける**（ここが起点で、切り分けが雑だと候補も出てこない）
- 提示された候補について、**そのオペレータが何を保証しているのか、変えると何を失うのか** を調べる
- `mergeMap` の同時実行数が無制限になる、という **副作用に自分で上限をかける**
- 前後を計測して、**効いていることを確認する**

候補を出すところは AI のほうが速い。**一方で「何が問題なのか」を定義するのと、「その対応で何を引き換えにしたのか」を引き受けるのは、まだこちらの仕事だと感じています。** 上限値を 6 に決めたのも、計測して自分で選んだ結果でした。

同じような進め方をしている方がいれば、切り分けと副作用の確認に時間を使う価値がある、という話として読んでもらえればと思います。
